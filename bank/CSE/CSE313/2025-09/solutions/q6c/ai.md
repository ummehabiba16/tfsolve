LFS buffers everything generated by these two writes -- data blocks, the files' inodes, and the directory update -- in memory and flushes it all together as one sequential run at the tail of the log. For 4 blocks written to `A.txt` and 3 blocks written to `B.txt`, both inside directory `exam`, the resulting segment (in the order this information becomes available) looks like:

$$\Big[\,A_0\;A_1\;A_2\;A_3\,\Big]\;\Big[\,I_A\,\Big]\;\Big[\,B_0\;B_1\;B_2\,\Big]\;\Big[\,I_B\,\Big]\;\Big[\,\text{exam's dir data (entries "A.txt"}\to I_A\text{, "B.txt"}\to I_B\text{)}\,\Big]\;\Big[\,I_{exam}\,\Big]$$

where $A_0..A_3$ are `A.txt`'s four data blocks, $I_A$ is `A.txt`'s inode (pointing at $A_0..A_3$), $B_0..B_2$ are `B.txt`'s three data blocks, $I_B$ is its inode, followed by `exam`'s updated directory-data block (now containing entries for both new files) and, if it needs updating too, `exam`'s own inode. The segment also carries a **segment summary block** (used later for crash recovery and segment cleaning, listing which file/block each piece of the segment belongs to), and the locations of $I_A$, $I_B$ (and $I_{exam}$, if changed) are recorded via updates to the **inode map (imap)**, since in LFS an inode's location changes every time it (or its data) is written.

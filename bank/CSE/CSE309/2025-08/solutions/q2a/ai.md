The textbook gives three reasons; the first is the most important for clarity of design.

**1. Simplicity of design.**

- The lexer deals with characters: it removes white space and comments and groups characters into tokens using **regular expressions/finite automata**. The parser deals only with a clean stream of tokens and the **context-free structure**.
- If the parser had to handle white space and comments, the grammar would need rules such as `E -> E ws? + ws? T` everywhere, and would become large and hard to read.
- Each phase uses the formalism that suits it: regular expressions for tokens, CFGs for syntax. Each can be designed, tested and debugged separately, and generated by a tool (Lex for the lexer, Yacc for the parser).
- A new language feature usually touches only one phase. For example, changing the form of numbers or identifiers changes only the lexer.

**2. Efficiency.** The lexer can use specialised techniques (buffer pairs with sentinels, a DFA-driven scanner) for the most time-consuming part of compilation, reading characters. Doing this inside a general parser would be slower.

**3. Portability.** Input-device peculiarities and character-set issues (line endings, encodings, trigraphs) are confined to the lexer; the rest of the compiler is unchanged.

**Example:** for `count = count + 1; // add`, the lexer delivers `<id,1> <=> <id,1> <+> <num,1> <;>`. The comment and spaces are gone, so the parser rule `stmt -> id = expr ;` stays simple.

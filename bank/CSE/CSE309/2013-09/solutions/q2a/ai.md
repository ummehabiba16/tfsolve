| | Top-down parsing | Bottom-up parsing |
|:--|:--|:--|
| Tree construction | from the **root** (start symbol) down to the **leaves** | from the **leaves** (the input tokens) up to the **root** |
| Derivation | **leftmost** derivation, in the order of the derivation | **rightmost** derivation, found in **reverse** |
| Main action | **expand** a nonterminal by a production (predict), match a terminal | **shift** input onto a stack and **reduce** a handle to the head of a production |
| Decision | which production to use for a nonterminal, using the lookahead | when to reduce and by which production, after the whole body has been seen |
| Methods | recursive descent, LL(1) predictive parsing | shift-reduce: operator precedence, LR(0), SLR, LALR, canonical LR |
| Grammar restrictions | no left recursion, left factoring needed, LL(k) grammars | handles left-recursive grammars; LR(k) grammars |
| Class of grammars | smaller (LL $\subset$ LR) | larger |
| Implementation | easy to write by hand | usually generated by a tool (Yacc, Bison) |

**Which is used in commercial compilers, and why.** The bottom-up (LR) method is the one used by the parser generators of many commercial compilers (Yacc/Bison-generated parsers), because:

1. **LR grammars are a larger class** than LL grammars and cover almost all programming-language constructs; the grammar need not be rewritten (no elimination of left recursion, no left factoring), so it stays natural and the semantic actions are easier to attach.
2. LR parsers detect a **syntax error as soon as possible** in a left-to-right scan (they have the viable-prefix property).
3. **Parser generators automate** the construction of LALR(1) tables, which are compact and efficient (linear time).

(Many production compilers, such as GCC and Clang for C and C++, use hand-written recursive-descent parsers, which give better error messages and handle context-dependent syntax; the bottom-up method is the dominant one in generated parsers.)
